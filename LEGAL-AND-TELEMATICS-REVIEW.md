# Settlement model and legal/telematics review

## Status and boundary

Draft v0.5 introduced, and v0.6 keeps, the structural corrections below. It is intended to make the data model and its evidence requirements explicit; passing SHACL or the competency-question suite does **not** demonstrate that an allocation is legally correct, that a message exchange is authorized, or that a meter is certified. The records in `era-energy-settlement-examples.ttl`, including authority and retention references, are illustrative placeholders.

The cited legal material and the applicable implementation guides must be verified against the operative official text before production use. This review has not independently confirmed Regulation (EU) 2026/253, the precise TEL TSI timing exception, ENE TSI market-interface duties, national settlement rules, or contract terms.

## Changes addressing the review findings

| Finding | Change in this draft | Remaining verification |
|---|---|---|
| Allocations linked whole readings without defining quantities or splits | `ens:AllocationComponent` records the consumed, regenerated, and net quantity attributed to one source reading (or a source-less estimate). Allocation totals are explicit and must equal their component sums. Component allocations are checked against the source reading so the total attributed across allocations cannot exceed the measured amount. | Confirm whether settlement is based on gross import, net energy, separate regeneration credit, or another rule. Add currency/price and loss adjustments only from the relevant contract/regulation; energy amounts are not invoice totals. |
| Operational train number was used as run identity; RU code was an unlinked string | `ens:RunningTrain` (identified by its operational train number identifier and departure date since 0.9) has a separate stable run ID, operational number, validity interval, consumer role, and actual-departure/evidence pair. Messages link to one run; shapes require matching message/run numbers and report times within the run interval. The source `era:responsibleRU` string is preserved and linked to the responsible RU's organisation role (`ens:responsibleRailwayUndertaking`, v0.8); the example code mapping is explicitly synthetic. | Agree the production run key and code registry, determine the correct consumer under each path/traction contract, and govern changes in RU responsibility over time. A reused operational number alone is not a run key. |
| Message annotations could be mistaken for proof of legal sharing | Replaced `ens:sharedWith` with `ens:DataExchangeActivity`: a specific message/version, sender, settlement recipient, time, outcome, purpose, authority reference, and retention-policy reference. A payload digest can be captured where available. | Populate authoritative references and transport acknowledgements. Enforce recipient authorization, access control, security, deletion, and retention in the exchange system; an RDF reference is not an authorization mechanism or GDPR compliance proof. |
| Reported test result could not be reproduced; some CQs tested less than their wording | Added the missing SHACL file and a vendored ERA ontology snapshot, made the runner default to it, corrected consumption-point identity and date-filtered queries, and added CQs for exchange evidence, organization resolution, and allocation quantities. The runner also runs negative identity/allocation cases and checks component sums and source caps. | The executable questions demonstrate behavior only for the synthetic graph. Expand the test data for multi-day runs, reused train numbers, multiple consumers, corrections, estimated components, mixed time zones, and splits before treating the model as production-ready. |
| EVN comparison stripped arbitrary punctuation and obscured the source value | Keep the original `era:locoNumber`, `era:vehicleNumber`, and consumption-point ID. The documented normalization removes only ASCII spaces and hyphens and accepts only a 12-digit normalized value. SHACL enforces equality for both the consumption-point relation and derived telematics vehicle match. | Confirm EVN formatting/check-digit rules with the authoritative register and implement any required check-digit validation. The current rule intentionally does not guess a checksum algorithm. |
| Units, actual-time evidence, quality, and meter evidence were underspecified | Reactive energy now uses QUDT `unit:KiloVAR-HR`; energy quantities carry unit annotations. Each reading has a quality concept. Actual departure is distinct from booked departure and must pair with an evidence reference. Late composition messages need assessment, evidence, and an authority reference. EMS approval/calibration evidence can be linked using `ens:measurementEvidence`. | Confirm the authoritative train-weight unit with ERA. Map a real source for actual departure. Verify exact legal timing windows, qualifying exceptions, and evidence requirements before enforcing them; the shapes require evidence links but do not implement the legal test. Obtain calibration/approval data under EN 50463 and deployment rules. |

## Required deployment decisions

Before using this for billing or regulatory evidence:

1. **Legal mapping:** record the exact operative instrument, article/annex/paragraph, effective dates, jurisdiction, responsible party, permitted recipient, purpose, and any exception. A populated `ens:exchangeAuthority` is only a citation pointer; have counsel or the competent regulatory expert confirm that it applies.
2. **Data protection and confidentiality:** determine whether the data is personal or otherwise protected in the actual context; document controller/processor roles, purpose limitation, data minimization, lawful basis where required, data-subject handling where applicable, recipient authorization, security, retention/deletion, and audit obligations. Train/vehicle identifiers are not automatically personal data, but association with individuals can change that assessment.
3. **Message integrity:** use source message IDs and version/correction semantics, authenticated sender/recipient identities, acknowledgements, and an integrity mechanism (digest/signature) appropriate to the transport. RDF links alone do not prove origin or receipt.
4. **Settlement rule:** agree component allocation and conservation, energy direction, regeneration credit, network-loss treatment, estimation and fallback, rounding, adjustment/reversal, and dispute workflows. Represent rule version and evidence for each result.
5. **Operational identity/time:** bind all messages and readings to a stable train run; source actual departure from an approved operational event. Do not infer it from the first location report unless the governing process expressly defines that derivation.
6. **ERA alignment:** test the extension against the exact deployed ERA ontology release and telematics application guide; raise upstream changes through ERA governance rather than treating local predicates as ERA requirements.
